# Communication architecture options

These hypotheses vary the information the receiver sees. The same carrier, authenticated peer context, policy checks, task fixtures, and scoring apply across the main comparisons. A2A used directly is a separate reuse control because the carrier already provides useful message and task structure. See the [literature review](../research/LITERATURE_REVIEW.md) for evidence and the [benchmark plan](../benchmarks/BENCHMARK_PLAN.md) for tests.

| Option | Representation and hypothesis |
| --- | --- |
| A. Natural language | Short written handoffs with ordinary headings and explicit uncertainty, constraints, provenance, and result wording. A strong baseline because most agent APIs can consume it directly. |
| B. Structured semantic interchange | Typed, versioned data and explicit relationships. Defined status and evidence fields may reduce misinterpretation and make mechanical validation possible. Use JSON in the first experiment. |
| C. Compact symbolic notation | Fixed, versioned codebook and grammar for the same information, with bounded literals and references for details the vocabulary cannot express. Savings depend on model tokenizers, glossary reuse, and decoding accuracy. |
| D. Hybrid semantic interchange | B's inspectable core plus typed optional prose, binary artifacts, or native payloads. Keep decision-critical claims and conditions in the core. First test text and artifact references, then isolate any latent experiment. |
| E. Agent-negotiated vocabulary | A per-session dictionary agreed on by independent agents before use, with a stable bootstrap format, dictionary digest, bounded negotiation, explicit acceptance, and fallback. Test whether repeated exchanges amortize setup and whether unfamiliar receivers can recover. |

| Criterion | A. Prose | B. Structured | C. Symbolic | D. Hybrid | E. Negotiated |
| --- | --- | --- | --- | --- | --- |
| Semantic fidelity | Expressive. Implicit scope and tense invite ambiguity. | Explicit distinctions. Schema can omit unforeseen nuance. | Depends on compositional grammar and escape rules. | Core supports decisions. Optional detail can add nuance or conflict. | Local vocabulary may fit well. Definitions can diverge. |
| Cross-model compatibility | Broad text access, variable interpretation. | Broad text or adapter access, uneven schema-following. | Requires usable glossary and tokenizer-aware testing. | Core travels across hosts. Native payload support varies by peer. | Requires peers that can complete bootstrap and apply the agreed grammar. |
| Encode/decode overhead | Few adapter steps. Free-form grounding can consume inference time. | Schema rendering, parsing, validation, possible repair. | Codebook setup, grammar validation, and decoding. | Core validation plus reference resolution or specialized decoding. | Extra negotiation and cache work followed by per-message checks. |
| Token and compute cost | Verbosity and rereading can dominate. | Repeated keys and schema instructions can dominate small tasks. | Might reduce tokens on repeated handoffs. Count setup and retries. | References may save context. Fetch, decode, or latent prefill can move costs. | Amortization depends on session lifetime, reuse, and each tokenizer. |
| Error propagation | Fluent summaries may silently drop negation or uncertainty. | Invalid structure can be rejected. Valid false statements still propagate. | Wrong symbol or stale dictionary can invert meaning. | A missing payload can block a decision. Core can preserve a readable failure. | Drift can corrupt many steps before it is noticed. |
| Security and trust | Embedded instructions are untrusted input. | Validate data and enforce permissions externally. | Obscured commands require a trusted decoder and the same policy boundary. | Check reference access, integrity, resource bounds, and parser safety. | Peers must never negotiate permissions or executable behavior through the dictionary. |
| Version compatibility | Wording can evolve but compatibility is implicit. | Pin schema, fail closed on unknown required meaning. | Pin grammar and dictionary independently. | Pin core and each optional payload profile. | Pin accepted dictionary to peers and session. Renegotiate after change. |
| Scalability | Fan-in can repeat large context. | Correlation and evidence references support routing and deduplication. | Shared dictionaries can pay off under repetition. Pair-specific glossary state increases with peers. | Selective retrieval can help fan-in. Storage, queueing, and reference access still cost. | Pairwise negotiations can grow quadratically under all-to-all traffic. |
| Debugging and inspection | Direct reading, manual comparison. | Mechanical validation and predictable rendering. | Requires exact codebook and readable rendering. | Inspectable core plus retained artifacts. Opaque content needs additional tooling. | Reconstruction requires the exact version and negotiation transcript. |
| Implementation complexity | Low format cost. Repair and auditing may require tools. | Moderate schema, vocabulary, validation, and migration work. | More grammar, escaping, and compatibility work. | Adds payload validation, capability matching, and fallback work. | Highest state, compatibility, timeout, and drift burden of the text-accessible options. |

## Testable differences

B earns a role only if independent receivers retain consequential distinctions more reliably than a documented prose handoff and an A2A-only mapping. D earns additional scope if a second payload channel improves outcomes or reduces end-to-end cost enough to justify its overhead. Compare C with both A and a terse schema baseline to isolate symbolic compression from simpler formatting choices. Evaluate E first on repeated sessions and include first contact, glossary disagreement, and peer replacement.

Binary serialization is a wire optimization until it changes what the model consumes. A smaller CBOR message rendered as the same JSON to the receiver can save network bytes while leaving model tokens unchanged. Pure latent exchange is a useful optional ablation inside compatible model pairs. Hidden-state access, compatibility, verification, and fallback are empirical requirements. An API that accepts text only counts as unsupported for that latent arm.
